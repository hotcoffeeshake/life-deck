# 建议适用前提

分类决定建议属于哪方面，适用前提决定当前是否可以向这个用户推荐。前提是本产品的编辑标注，不是 GitHub 原作者的标签，也不是用户画像推断结果。

608 条原文建议逐条登记在 [建议适用前提.tsv](建议适用前提.tsv)。原文、标题、章节和原始成本收益未改动。完整建议库仍可查看，推荐池先过滤适用前提，再计算兴趣顺序。

## 匹配规则

- `general`：可用于日常预防、通用方法探索。并不保证每个人都需要实施，原文条件仍须阅读。
- `conditional`：`requires` 的每个条件都要经用户明确确认。未确认等同于暂不进入推荐池。
- 不认识的卡片 ID 不进入推荐池。
- 新选“正在找工作”仅确认求职，新选明确在职阶段仅确认在职；其余阶段、喜欢某个方面或收下某张卡，不确认工伤、疾病、怀孕、创业或网站经营等事实。旧存档的人生阶段不自动转为已确认事实。
- 求职与失业分开；在职与劳动纠纷分开；劳动纠纷与工伤分开；从事技术工作与运营网站分开。
- 为了方面覆盖不能越过适用前提。一个方面的通用卡片已用尽时可以延后，不能拿该方面的专业建议填空。

住房与家人仅一条无需额外前提的维修报价防护建议。租房、买房、生育、育儿、照护、丧事本身都有前提，不能为增加数量改标通用。

通用健康条目包括生活方式、消费避坑与公共急救知识；出现疾病确诊、特定症状、年龄筛查、孕产、儿童、残疾等适用条件的条目另加前提。`specific_health` 仅表示有特定医疗条件，不代表系统判断了疾病或年龄。每条带此标记的建议还要求独立的 `health_source_章节_序号` 前提，确认名称逐字附上该条原文标题，用户必须核对原文条件后单独确认。确认糖尿病眼底建议不会解锁肾结石、痛风、其他症状或年龄筛查建议。`chronic_care` 或 `specific_health` 本身都不足以解锁这些条目。此确认是用户核对适用条件，不是系统诊断。

## 接口

加载顺序：`catalog.js` 后加载 `applicability.js`，推荐引擎之前加载。

- `LifeApplicability.contexts`：可确认的前提 ID 和中文名称。
- `LifeApplicability.get(cardOrId)`：返回 `{requires,reason,mode}`；未知 ID 返回 `null`；返回副本，不能意外修改内部规则。
- `LifeApplicability.eligible(cardOrId,flags)`：所有前提已确认才返回 `true`。不根据人群或兴趣分数扩充 flags。

例：`eligible('source-19-14',['job_search'])` 为 false；`eligible('source-19-14',['work_injury'])` 为 true。
